一、学习闭环（self-improving loop）

学习闭环由四块构成，它们各管一段、首尾相接：

环节负责模块沉淀的东西触发时机
记忆系统agent/memory_manager.py、agent/memory_provider.py、plugins/memory/*用户画像、环境事实、跨会话记忆每轮后台同步 + nudge
技能系统skills/、agent/skill_*.py、agent/learn_prompt.py可复用的程序性知识（SKILL.md）自动创建 + /learn 手动
后台复盘agent/background_review.py、agent/turn_finalizer.py把"刚刚这轮"学到的写进记忆/技能每 N 轮 nudge fork
Curator 策展agent/curator.py维护整个技能库的健康度空闲时周期触发
跨会话召回tools/session_search_tool.py把历史会话变成可检索语料按需 FTS5 检索
为什么这让 Hermes 能自我改进？闭环的每一环都把"这次会话学到的东西"沉淀成下次会话开场就已知的状态。每次会话不是从零开始，而是从"上次结束时对你的理解"开始——理解只增不减，越用越深。

二、记忆系统：持久画像如何跨会话积累

两层内置记忆

内置记忆是两个 Markdown 文件，定义见 tools/memory_tool.py:6：

MEMORY.md

agent 的个人笔记与观察（环境事实、项目约定等）。

USER.md

agent 对用户的了解（偏好、沟通风格、期望）。

MemoryStore（tools/memory_tool.py:109）负责从这两个文件加载条目，并在系统提示词里快照注入。这意味着 agent 每次会话开场，系统提示词里就已经带着"它对你的全部了解"——这是跨会话连续性的最底层机制。

可插拔的外部记忆后端

抽象基类是 agent/memory_provider.py:43 的 MemoryProvider(ABC)，核心生命周期方法：

  • initialize() 连接/建表/预热
  • system_prompt_block() 注入静态记忆文本
  • prefetch(query) 每轮前后台召回
  • sync_turn(user, asst) 每轮后异步写入
  • get_tool_schemas() / handle_tool_call() 暴露并分发记忆工具
  • 可选钩子：on_session_end（会话结束抽取）、on_pre_compress（压缩前抢救）、on_delegation（观察子 agent 工作）
单 provider 约束：同一时间只允许一个外部 provider（agent/memory_manager.py:6-8），注册第二个会被拒绝并告警——这是为了避免工具 schema 膨胀和后端冲突。

内置记忆后端插件

honcho（辩证式用户建模） hindsight mem0 byterover openviking retaindb supermemory holographic

以 Honcho 为例（plugins/memory/honcho/__init__.py:191）：实现"辩证式用户建模"——在后台跑多轮辩证 prompt 来推断"你是谁"，并在每轮前通过 prefetch 把召回结果喂进上下文。这正是 README 里 "Honcho dialectic user modeling" 的实现。

三、技能系统：完成复杂任务后自动沉淀程序性知识

如果说记忆是"agent 知道什么"，技能就是"agent 会做什么"——程序性记忆。

技能格式（兼容 agentskills.io 标准）

每个技能是一个 SKILL.md，带 YAML frontmatter + 正文。仓库内置 72 个 SKILL.md，按领域分目录（skills/creative、skills/software-development、skills/github、skills/research、skills/mlops 等约 18 个大类）。

---
name: test-driven-development
description: "TDD：强制执行 RED-GREEN-REFACTOR，先写测试再写代码。"
version: 1.1.0
author: Hermes Agent (adapted from obra/superpowers)
platforms: [linux, macos, windows]
metadata:
  hermes:
    tags: [testing, tdd, development, quality]
---
最关键的一条规则（agent/learn_prompt.py:40-44）：description 必须 ≤60 字符——因为系统提示词里的技能索引会把描述截断到 60 字，超出部分会被静默截掉、永远无法路由。所有技能的简短描述常驻系统提示词，agent 据此决定何时加载哪个技能的完整正文。

技能的调用与预处理

agent/skill_commands.py

CLI 与 gateway 共享的 /skill-name 斜杠命令分发。调用时把这一轮展开成嵌入完整技能正文 + 脚手架的"模型可见消息"。

agent/skill_preprocessing.py

SKILL.md 的模板预处理。支持 ${HERMES_SKILL_DIR} / ${HERMES_SESSION_ID} 变量替换和内联 shell 片段 !`date`（输出截断到 4000 字）。

agent/skill_bundles.py

技能"捆绑包"。一个 YAML 把多个技能聚合到一个斜杠命令下，/<bundle> 一次加载 N 个技能。冲突时 bundle 优先于同名 skill。

自动创建 / 自我改进——/learn 与后台复盘

手动 /learn（agent/learn_prompt.py）

用户可以把 /learn 指向任何能描述的东西——代码目录、API 文档 URL、"我刚刚带你走过的流程"。build_learn_prompt 构造一个 prompt，指示当前活着的 agent用它已有的工具去搜集素材并通过 skill_manage 写出符合标准的 SKILL.md。没有独立的"蒸馏引擎"，无额外模型工具足迹。

自动后台复盘（agent/background_review.py）

每完成 N 轮工具调用，turn_finalizer 触发一次后台技能复盘。机制是 fork 一个 agent，重放整轮对话，问它"该不该保存/更新某个技能？"——写入直接落到技能库，主会话和 prompt cache 完全不受污染。

后台复盘的产品意图（agent/background_review.py:170-204）：
"Review the conversation above and update the skill library. Be ACTIVE — most sessions produce at least one skill update. A pass that does nothing is a missed learning opportunity, not a neutral outcome."

用户的挫败信号（"stop doing X"、"this is too verbose"、"remember this"）是一等技能信号——应当把偏好直接编码进相关技能，让下次会话开场就已经知道。

nudge 节奏的配置

  • 技能 nudge：agent._skill_nudge_interval（默认 10，配置键 skills.creation_nudge_interval，agent/agent_init.py:1197-1200），每次实际用了 skill_manage 就重置计数。
  • 记忆 nudge：agent._memory_nudge_interval（默认 10，配置键 memory.nudge_interval，agent/agent_init.py:1105-1113）。

四、Curator：周期性策展整个技能库

后台复盘负责"往库里加东西"，Curator 负责"维护这个库不烂掉"（agent/curator.py）。

触发方式

空闲触发，无 cron 守护进程。当 agent 空闲且距上次运行超过 interval_hours（默认 7 天）时，maybe_run_curator() 派生一个 fork 出来的 agent 做审查。

职责

根据技能活动时间戳自动转换生命周期状态（stale→archive 等）；对 agent 创建的技能执行 pin / archive / consolidate / patch；状态持久化在 ~/.hermes/skills/.curator_state。

严格不变量（安全设计）

  • 只操作 agent 创建的技能（绝不动用户手写的技能，靠 tools/skill_usage.is_agent_created 判定）。
  • 从不自动删除——只归档，归档可恢复。
  • 被 pin 的技能跳过所有自动转换。
  • 使用辅助模型客户端，从不触碰主会话 prompt cache。
  • DEFAULT_CONSOLIDATE = False（:62）：确定性的非活动剪枝照常跑，但需要 LLM 开销的"主观合并"流程默认关闭，避免烧钱。

五、跨会话搜索：FTS5 + 锚点窗口召回

tools/session_search_tool.py 是单一形态工具，三种模式由参数推断：

模式触发条件行为LLM 开销
发现（DISCOVERY） 传 query 跑 SQLite FTS5 全文索引，按会话血缘对命中去重，返回前 N 个会话，每个附带匹配位置 ±5 条的窗口，外加 bookend（会话最早/最晚各 3 条 user+assistant）。 零
滚动（SCROLL） 传 session_id + around_message_id 返回锚点 ±window 的窗口，可反复把窗口边缘消息当新锚点向前/后翻。 零
浏览（BROWSE） 不传参数 按时间倒序返回最近会话列表。 零
注意：README 提到 "FTS5 session search with LLM summarization"，而当前实现注释（tools/session_search_tool.py:23-26）明确说"把所有模式合并为单一调用形态，没有 summary LLM 路径"。早期 PR（#20238）曾有 fast/summary 双模式，现已合并精简。README 的 LLM 摘要措辞与现状略有出入，以代码为准。
子 agent 委派的会话默认从搜索/浏览里隐藏（tools/session_search_tool.py:35：subagent、tool 来源被排除），保证检索到的是真正的用户会话历史。

六、消息网关 gateway/

"Lives where you do：Telegram, Discord, Slack, WhatsApp, Signal, and CLI — all from a single gateway process."

单进程多平台

入口是 gateway/run.py：start_gateway() 启动所有已配置的平台适配器，GatewayRunner 管理网关生命周期。它是一个长驻守护进程（gateway/run.py:52 注释强调）。

平台适配器注册表

网关不靠硬编码的 if/elif 链发现平台，而是用注册表 gateway/platform_registry.py。PlatformEntry（:38）是单个平台的元数据 + 工厂：name、label、adapter_factory（接收 PlatformConfig 返回 adapter 实例）、check_fn（依赖是否可用）等。插件侧通过 platform_registry.register(PlatformEntry(...)) 注册。

已支持的平台

Telegram Discord Slack WhatsApp Signal Email Feishu Teams Line Matrix Mattermost IRC SMS DingTalk WeCom Google Chat Home Assistant NTFY QQbot 微信/元宝

跨平台会话连续性

会话管理在 gateway/session.py（:1-9），负责：会话上下文跟踪、对话持久化到磁盘、重置策略评估、动态系统提示注入（让 agent 知道自己当前在哪个上下文里）。配合 PII 脱敏（把发送者 ID 哈希成 user_<12hex>）。

因为会话状态是平台无关地持久化的，所以你可以在 Telegram 起个话题、切到 Discord 继续——这就是 README 说的 "cross-platform conversation continuity"。

七、定时任务 cron/

"Scheduled automations：Built-in cron scheduler with delivery to any platform … all in natural language, running unattended."

调度执行（cron/scheduler.py）

tick()：检查到期任务并运行，网关每 60 秒从后台线程调用一次。用文件锁 ~/.hermes/cron/.tick.lock 保证多进程重叠时只有一个 tick 在跑（Unix fcntl，Windows 回退 msvcrt）。

任务存储（cron/jobs.py）

任务存于 ~/.hermes/cron/jobs.json，每次运行的输出落到 ~/.hermes/cron/output/{job_id}/{timestamp}.md。用 croniter 解析 cron 表达式。jobs.json 的临界区用跨进程文件锁保护。

面向 agent 的工具（tools/cronjob_tools.py）

暴露一个压缩的、面向动作的单工具（避免 schema/上下文膨胀），内部封装 create_job / list_jobs / update_job / pause_job / resume_job / remove_job / parse_schedule 等。

自然语言与蓝图

cron/blueprint_catalog.py、cron/suggestions.py 提供任务蓝图与建议（常见自动化模板：日报、夜间备份、周审计）。cron/scheduler_provider.py 让 cron provider 可插拔。

工作原理：agent 用自然语言描述"每天早上 8 点给我发昨天的 GitHub 摘要到 Telegram"，工具把它落成一条 cron job，调度器到点 fork 一个 agent 执行并把结果投递到指定平台。安全上，tools/cronjob_tools.py:48- 起有针对"用户提供的 cron 提示词"和"agent 自己写的提示词"两个威胁面的扫描器。

八、插件与 providers：一切皆可插拔

plugins/——按能力域分目录的插件树

插件目录内容
plugins/model-providers/模型提供商（deepseek、gemini、nous、openrouter、novita、nvidia、xai、kimi-coding、minimax 等约 20 家）
plugins/memory/记忆后端（见第二节）
plugins/platforms/聊天平台适配器（见第六节）
plugins/web/网页搜索 provider（brave_free、ddgs、exa、firecrawl）
plugins/image_gen/、video_gen/图像/视频生成后端
plugins/observability/可观测性（langfuse）
plugins/browser、context_engine、cron_providers、kanban 等各类专项后端

providers/——推理 provider 的注册表与 ABC

注意区分（providers/README.md:1-25）：providers/ 只放注册表和 ProviderProfile 数据类（providers/base.py）；具体的 profile 本体作为插件住在 plugins/model-providers/<name>/。注册表在首次访问时惰性发现这些插件（get_provider_profile() / list_providers()）。

每个 provider 只声明一次 ProviderProfile，其余所有层（鉴权解析、传输 kwargs、模型列举、运行时路由）都从 profile 读，不再各自维护平行数据。这就是 README 说的 hermes model 一键切换、"no code changes, no lock-in" 的实现基础。

一句话区分：plugins/ 是"插件实现住的地方"，providers/ 是"模型 provider 的注册中枢"。

九、把闭环连起来：一次完整的"自我改进"

用一个场景串起本章，体会每一环的衔接：

  1. 1
    语音发起，网关转写 你在 Telegram（§6 网关）发语音说"以后给我写 commit message 别用感叹号"。语音被转写成文本。会话状态持久化（gateway/session.py），跨平台可续。
  2. 2
    后台复盘 fork，双线沉淀 这一轮结束，计数器到阈值 → 后台复盘 fork（§3，background_review.py）重放对话，识别出"用户纠正了风格"这个一等技能信号，把偏好 patch 进相关技能，同时把"你不喜欢感叹号"写进 USER.md（§2）。主会话毫无感知，prompt cache 不受污染。
  3. 3
    Curator 整理技能库 一周后空闲时，Curator（§4）巡检技能库，把这条偏好所在的技能往 class-level 形状收拢，归档掉过时的窄技能。
  4. 4
    新会话开场即已知 下次你在 Discord 开新会话——系统提示词开场就带着 USER.md 的画像和那条技能的描述索引。你不用再说一遍，agent 已经知道。
  5. 5
    跨会话搜索召回 三个月后你忘了当时怎么配的某个流程，用会话搜索（§5，FTS5）一搜就翻回当时的上下文。
  6. 6
    cron 无人值守 你还可以让它把"每周技能审计报告"设成 cron（§7），无人值守地发到你手机。
