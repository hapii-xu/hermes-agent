# 02 · 整体架构与启动 / 入口流程

## 本章导读

这一章带你从「用户在终端敲下 `hermes`」开始，一路追到 agent 核心被拉起的全过程，并把项目的整体架构分层、进程模型、关键顶层模块、配置体系讲清楚。读完你应该能回答：

- 三个入口脚本（`hermes` / `hermes-agent` / `hermes-acp`）分别干什么？
- `hermes` 命令背后的调用链是怎样的？
- 什么是「窄腰（narrow waist）」设计？为什么核心要保持克制？
- CLI、gateway、MCP server、memory server 这些进程怎么分工？
- `cli.py`、`run_agent.py` 这些上万行的「god file」各自负责什么？
- `config.yaml` 和 `.env` 的边界在哪里？

所有代码引用都用 `文件:行号` 形式，方便在编辑器里点击跳转。

## 1. 三个入口脚本（`[project.scripts]`）

入口在 `pyproject.toml:296-299` 定义：

```toml
[project.scripts]
hermes = "hermes_cli.main:main"
hermes-agent = "run_agent:main"
hermes-acp = "acp_adapter.entry:main"
```

| 命令 | 入口函数 | 职责 |
|------|---------|------|
| `hermes` | `hermes_cli/main.py:12022` 的 `main()` | **面向人类用户的主 CLI**。这是日常入口：交互式聊天、`gateway` / `setup` / `cron` / `model` / `doctor` / `mcp` / `honcho` 等所有子命令的总调度。内部用 argparse 构建一棵庞大的子命令树。 |
| `hermes-agent` | `run_agent.py:5357` 的 `main()` | **agent 核心的直接运行器 / 库入口**。把 `AIAgent`（`run_agent.py:334`）作为一个独立、可嵌入的「带工具调用的对话循环」暴露出来。可用 `fire` 当 CLI 跑（`run_agent.py -q "..."`），也被 `cli.py`、`batch_runner.py`、RL 环境作为库 `from run_agent import AIAgent` 导入。它是「裸 agent」，不带 TUI/REPL。 |
| `hermes-acp` | `acp_adapter/entry.py` 的 `main()` | **ACP（Agent Client Protocol）服务器适配器**，用于编辑器集成（如 acp-bridge）。从 `~/.hermes/.env` 加载环境，把日志全部导到 stderr，**stdout 留给 ACP 的 JSON-RPC 传输**，然后启动 ACP agent server。等价于 `hermes acp` 子命令（`acp_adapter/entry.py:1-13`）。 |

**三者的共同点**：每个入口文件的**第一件事**都是 `import hermes_bootstrap`（见 `hermes_cli/main.py:59`、`run_agent.py:25`、`acp_adapter/entry.py:17`），且都用 `try/except ModuleNotFoundError` 包裹——原因见第 5、4 节。

## 2. 启动链路：敲下 `hermes` 之后发生了什么

以最常见的「交互式聊天」为例（直接 `hermes` 或 `hermes chat`）：

```
用户在 shell 敲 `hermes`
        │
        ▼
[1] pyproject 的 console_script 调到 hermes_cli/main.py:main()  (line 12022)
        │  ① import hermes_bootstrap      → Windows 上设 UTF-8 stdio（POSIX 空操作）
        │  ② _set_process_title()         → ps/top 里显示 "hermes" 而非 python3.11
        │  ③ configure_windows_stdio()    → 二次确保 Windows stdio UTF-8
        │  ④ _cleanup_quarantined_exes / _recover_from_interrupted_install
        │       → 自愈上一次 `hermes update` 留下的半成品
        │  ⑤ Termux 快速启动短路（_try_termux_fast_*_launch）
        │
        ▼
[2] build_top_level_parser()  (hermes_cli/_parser.py)
        │  构建 argparse 子命令树；无子命令时默认 func = cmd_chat
        │  逐个注册 model / fallback / secrets / migrate / gateway / cron ... 子命令
        │
        ▼
[3] 解析 argv → 分发到对应的 cmd_* 函数
        │  这里走 cmd_chat()  (hermes_cli/main.py:2203)
        │
        ▼
[4] cmd_chat()
        │  · 解析 -c/--continue、--resume（按标题或 ID 解析历史会话）
        │  · 首次运行守卫：_has_any_provider_configured()，没配 provider 就引导 `hermes setup`
        │  · 同步内置 skills、处理 --yolo / --safe-mode / --source 等开关
        │  · _resolve_use_tui(args) 决定走 TUI 还是经典 CLI
        │
        ├──(TUI)──► _launch_tui(...)             (main.py:2350) → 拉起 tui_gateway / Electron 前端
        │
        └──(CLI)──► from cli import main as cli_main; cli_main(**kwargs)   (main.py:2369)
                        │
                        ▼
[5] cli.py:main()  (cli.py:14986)
        │  · 再次 configure_windows_stdio()
        │  · gateway=True 时直接 asyncio.run(start_gateway())（少见路径）
        │  · 处理 git worktree 隔离（-w）
        │  · 构造 cli = HermesCLI(...)            (cli.py:15132)
        │       HermesCLI(CLIAgentSetupMixin, CLICommandsMixin)  (cli.py:3358)
        │  · cli._init_agent(...)                 (cli.py:11447) ← 真正创建 agent
        │       内部把 run_agent.AIAgent(...) 实例挂到 cli.agent
        │       （AIAgent 通过 cli.py:822 的薄代理懒导入，避免 OpenAI SDK 启动开销）
        │
        ▼
[6] 进入 prompt_toolkit 应用循环
        │  HermesCLI.run()  (cli.py:12401) → app.run()  (cli.py:14773)
        │  每次用户提交输入 → cli.agent.run_conversation(...)  (cli.py:11676 / 14938 / 15377)
        │
        ▼
[7] AIAgent.run_conversation()  (run_agent.py:5307)
           对话循环 = 调模型 → 解析 tool_calls → 执行工具 → 回填结果 → 直到收敛
           工具通过 model_tools.handle_function_call 分发到 tools/ 下的各处理器
           真正的循环细节在 agent/conversation_loop.py（4656 行）
```

要点：

- **`hermes_cli/main.py` 只做「路由 + 环境自愈」**，不含 agent 逻辑。它把交互式聊天**委托**给顶层的 `cli.py`。
- **`cli.py` 提供 TUI/REPL 外壳**（prompt_toolkit），并持有一个 `AIAgent` 实例（`cli.agent`）。
- **`run_agent.py` 的 `AIAgent` 才是 agent 核心**——可脱离 CLI 单独运行，也被 gateway、batch、RL 复用。这是「同一个 agent core 跑遍 CLI / gateway / TUI / desktop」的物理体现（见 `AGENTS.md:9-14`）。

## 3. 整体架构分层与「窄腰」设计

### 3.1 分层概览

```
┌──────────────────────────────────────────────────────────────────┐
│  边缘 (edges) —— 能力在这里疯狂生长，鼓励扩张                        │
│                                                                    │
│  hermes_cli/     CLI 子命令（setup/model/cron/mcp/doctor/...）       │
│  gateway/        消息网关：Telegram/Discord/Slack/Matrix... ~20 平台 │
│  tui_gateway/    TUI / Electron 桌面前端的后端桥                     │
│  cron/           内置定时调度器（croniter）                          │
│  plugins/        运行时发现的插件（平台适配器、搜索 provider 等）      │
│  providers/      provider 抽象基类（ABC）+ 编排，第三方接入点         │
│  skills/         技能（指令式 Markdown + 脚本），可自我创建/改进       │
│  tools/          ~100+ 工具实现，各自向 registry 自注册               │
│  acp_adapter/    编辑器集成 (ACP)                                    │
├──────────────────────────────────────────────────────────────────┤
│  窄腰 (narrow waist) —— 极度克制，每加一个核心工具都很贵             │
│                                                                    │
│  agent/          agent 核心（对话循环、上下文、记忆、压缩、prompt）   │
│  run_agent.py    AIAgent：带工具调用的对话循环                       │
│  model_tools.py  工具注册表之上的薄编排层（决定哪些工具上桌）         │
│  toolsets.py     工具集（命名分组，跨平台共享）                       │
└──────────────────────────────────────────────────────────────────┘
```

各目录职责一句话速记：

| 目录 / 模块 | 职责 |
|------|------|
| `agent/`（~90 个文件） | agent 核心实现：`conversation_loop.py`（对话循环）、`agent_init.py`（初始化）、`context_engine.py` / `context_compressor.py`（上下文与压缩）、`memory_manager.py`（记忆）、`system_prompt.py` / `prompt_builder.py`（系统提示）、`tool_executor.py`（工具执行）、各家 provider 的 `*_adapter.py`。这是「窄腰」的主体。 |
| `tools/` | 每个工具一个文件（`terminal`、`read_file`、`web_search`、`browser_*`、`delegate_tool` 等），通过 `tools/registry.py` 的 `register()` **自注册**。 |
| `toolsets.py` | 把工具按场景命名成「工具集」（research/development/safe...），并定义 CLI 与所有消息平台**共享**的核心工具列表 `_HERMES_CORE_TOOLS`（`toolsets.py:30`）。改一处，全平台同步。 |
| `gateway/` | 消息网关进程，单进程驱动 ~20 个平台适配器；入口 `gateway/run.py:start_gateway`（`gateway/run.py:17428`）。 |
| `hermes_cli/` | 所有 `hermes` 子命令的实现（setup、model、doctor、mcp catalog、plugins 发现等）。 |
| `cron/` | 内置 cron / interval 调度器（croniter 是核心依赖）。 |
| `plugins/` | 运行时发现的插件，带 `plugin.yaml` 清单；插件**只能**在自己的目录里、用核心提供的 ABC/hook 工作，不许碰核心文件（`AGENTS.md:122-125`）。 |
| `providers/` | provider 抽象层（`providers/base.py` 是 ABC）。当同一「类别」有多个竞争实现时，先设计 ABC + 编排器，再把竞品变成插件（`AGENTS.md:198-201`）。 |
| `skills/` | 技能：指令式 Markdown + 可选脚本。agent 能**从经验中自创建并在使用中改进**技能，兼容 agentskills.io 标准。 |

### 3.2 「窄腰（narrow waist）」是什么

出处：`AGENTS.md:18-27`。两条贯穿全项目的设计铁律：

1. **按对话的 prompt 缓存是神圣的**（`AGENTS.md:19-23`）。长会话每轮复用一段缓存前缀，任何中途改写历史、换工具集、重建系统提示的行为都会**击穿缓存**，让用户成本翻倍——所以坚决不做（唯一例外是上下文压缩）。
2. **核心是窄腰，能力住在边缘**（`AGENTS.md:24-27`）。**每一个核心 model tool 都会在每次 API 调用时被发送**，所以新增核心工具的门槛极高。大多数新能力应以「CLI 命令 + skill」「service-gated tool」「插件」「MCP server」的形式落在**边缘**，而不是长进核心。

对应的「足迹阶梯（Footprint Ladder）」（`AGENTS.md:171-196`），从最省到最贵：
**①扩展已有代码 → ②CLI 命令 + skill → ③服务门控工具(`check_fn`) → ④插件 → ⑤MCP server（进 catalog）→ ⑥新核心工具（最后手段）**。

一句话总结这套哲学（`AGENTS.md:43-50`）：**「在边缘扩张，在窄腰克制」**——产品面（平台/渠道/provider/模型/桌面功能）鼓励大胆增长，唯独 **核心 agent + model tool schema** 这一处要省到底，因为它在每次 API 调用上都要付费。

## 4. 进程模型

Hermes 是**多进程**架构。`hermes_logging.py:37-44` 的注释直接点名了同时写 `agent.log` 的多个独立进程：「TUI、gateway、`hy_memory` server、MCP servers，以及按需的 CLI 命令」。各进程分工：

| 进程 | 由谁启动 | 职责 |
|------|---------|------|
| **CLI / TUI 进程** | `hermes` / `hermes chat` | 前台交互式会话。持有一个 `AIAgent`，跑 prompt_toolkit 循环。 |
| **gateway 进程** | `hermes gateway start` → `gateway/run.py:start_gateway` | 常驻服务，单进程驱动所有消息平台适配器 + cron 投递。每个会话同样在内部用 agent core。 |
| **MCP server 进程** | `hermes mcp serve`（`mcp_serve.py`），或 catalog 里的外部 MCP server | stdio MCP 服务器，把「消息对话」作为 MCP 工具暴露给 Claude Code / Cursor / Codex 等外部 MCP 客户端；同时 agent 自己也能作为 MCP **client** 连接外部 MCP server。 |
| **memory server 进程**（`hy_memory`） | 记忆后端按需拉起 | 独立的记忆服务进程（与 `agent/memory_manager.py` / `agent/memory_provider.py` 配合）。*具体生命周期待确认*，但日志注释确认它是**独立进程**。 |
| **子进程（短命）** | agent 工具调用 | execute_code 沙箱、`delegate` 委派的子 agent、linter 等，由 agent 在工具执行时 `subprocess` 派生。 |

跨进程协作的两个细节：

- **日志**：所有进程都写 `~/.hermes/logs/`（`hermes_logging.py:2-21`）。`agent.log` 是兜底，`gateway.log` / `gui.log` 按组件 logger 名分流。Windows 上因为多进程同时持有 `agent.log` 句柄，标准库的 `RotatingFileHandler.doRollover()` 会因 `os.rename()` 触发 `WinError 32`，所以 Windows 专门换成 `concurrent-log-handler`（跨进程文件锁，`hermes_logging.py:37-60`、`pyproject.toml:124-137`）。
- **UTF-8 引导**：`hermes_bootstrap` 在每个入口顶端设置 `PYTHONUTF8` / `PYTHONIOENCODING`，**子进程继承**这些环境变量，从而让派生出的每个 Python 子进程也走 UTF-8（`hermes_bootstrap.py:9-26, 71-75`）。这是「父进程一次性引导、整条进程树受益」的关键。

## 5. 关键顶层模块速查表（含「god file」标注）

这些都是 `pyproject.toml:302` 的 `py-modules` 顶层模块。行数即「体量」，上万行者即典型 god file（`AGENTS.md:64-70` 明确把 `cli.py` / `run_agent.py` / `gateway/run.py` 列为可被重构拆分的 god file，且这类大型机械重构是**受欢迎**的工作）。

| 模块 | 行数 | 一句话职责 | god file? |
|------|------|-----------|-----------|
| `cli.py` | ~15,487 | 交互式终端外壳：prompt_toolkit TUI/REPL、`HermesCLI` 类、`main()` 入口，持有 `AIAgent`。 | **是（最大）** |
| `hermes_cli/main.py` | ~13,230 | `hermes` 命令的 argparse 路由 + 子命令注册 + 启动期环境自愈。 | **是** |
| `run_agent.py` | ~5,573 | `AIAgent` 类与对话循环；agent 核心，可作库/CLI 独立运行。 | **是** |
| `hermes_state.py` | ~5,103 | 基于 SQLite 的会话状态存储（WAL 并发 + FTS5 全文检索），存会话元数据/消息历史/模型配置（`hermes_state.py:2-15`）。 | **是** |
| `model_tools.py` | ~1,256 | 工具注册表之上的**薄编排层**：触发工具发现、决定哪些工具上桌、分发 `handle_function_call`（`model_tools.py:3-21`）。 | 偏大 |
| `mcp_serve.py` | ~903 | `hermes mcp serve` 的 stdio MCP 服务器，把对话作为 MCP 工具暴露（`mcp_serve.py:1-27`）。 | 中等 |
| `toolsets.py` | ~933 | 工具集定义 + 跨平台共享的核心工具列表。 | 中等 |
| `hermes_constants.py` | ~733 | **无依赖、导入安全**的共享常量（`get_hermes_home()` / `get_config_path()` 等，profile 感知）；可从任意处导入无循环风险（`hermes_constants.py:1-5`）。 | 否 |
| `hermes_bootstrap.py` | ~187 | Windows UTF-8 stdio 引导 + `harden_import_path()`；必须第一个被导入，POSIX 空操作（`hermes_bootstrap.py:1-45`）。 | 否 |

## 6. 配置体系：`config.yaml` vs `.env`

出处：`AGENTS.md:103-107`。两者职责**严格分离**，这是项目的硬规则：

| | `config.yaml`（示例 `cli-config.yaml.example`） | `.env`（示例 `.env.example`） |
|---|---|---|
| 存什么 | **所有行为设置**：默认模型、provider、超时、阈值、功能开关、显示偏好…… | **只存机密**：API key、token、密码。 |
| 位置 | `~/.hermes/config.yaml`（profile 感知） | `~/.hermes/.env` |
| 谁改 | `hermes setup` / `hermes model` / `hermes tools` 等命令，或手改 YAML | 用户填入凭证 |
| 优先级 | — | `.env` 里的环境变量**优先于** config（`cli-config.yaml.example:3`） |

硬性约束（`AGENTS.md:103-107`）：

- **禁止为非机密配置新增 `HERMES_*` 环境变量**。一切行为开关都进 `config.yaml`；即使内部机制需要一个环境变量做桥接，面向用户的文档也必须指向 `config.yaml`。
- 任何告诉用户「把 X 设进 .env」的 PR 会被拒——除非 X 是凭证。
- 示例印证：`.env.example:11-15` 明确写「默认模型在 `config.yaml` 的 `model.default` 里配，`LLM_MODEL` 不再从 `.env` 读」；而 `cli-config.yaml.example:8-40` 用一大段配置 `model.default` 和 `provider`，把对应**密钥**留给 `.env`。

记忆口诀：**凭证进 `.env`，行为进 `config.yaml`。**
