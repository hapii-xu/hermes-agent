# 04 · 核心特色功能：学习闭环、消息网关与定时任务

> **本章导读**
>
> 本章讲清楚 Hermes 区别于"普通 agent"的三大灵魂功能：
>
> 1. **学习闭环（self-improving loop）**——记忆、技能、Curator 策展、跨会话搜索如何咬合成一个闭环，让 agent 越用越懂你、越用越能干。这是项目 README 第一句话的卖点："the only agent with a built-in learning loop"。
> 2. **消息网关 `gateway/`**——单进程驱动约 20 个聊天平台，跨平台会话连续、语音转写。
> 3. **定时任务 `cron/`**——内置 cron 调度器，用自然语言描述定时任务并投递到任意平台。
>
> 外加两节背景：插件与 providers 体系（这些特色如何作为可插拔后端接入），以及 MCP / 子 agent / 个性化的简要提及。
>
> 阅读时请重点体会一个问题：**为什么这些设计让 Hermes 能"自我改进"？** 答案贯穿全章——闭环的每一环都把"这次会话学到的东西"沉淀成下次会话开场就已知的状态。

---

## 一、学习闭环（self-improving loop）

学习闭环由四块构成，它们各管一段、首尾相接：

| 环节 | 负责模块 | 沉淀的东西 | 触发时机 |
| --- | --- | --- | --- |
| 记忆系统 | `agent/memory_manager.py`、`agent/memory_provider.py`、`plugins/memory/*` | 用户画像、环境事实、跨会话记忆 | 每轮后台同步 + nudge |
| 技能系统 | `skills/`、`agent/skill_*.py`、`agent/learn_prompt.py` | 可复用的程序性知识（SKILL.md） | 自动创建 + `/learn` 手动 |
| 后台复盘 | `agent/background_review.py`、`agent/turn_finalizer.py` | 把"刚刚这轮"学到的写进记忆/技能 | 每 N 轮 nudge fork |
| Curator 策展 | `agent/curator.py` | 维护整个技能库的健康度 | 空闲时周期触发 |
| 跨会话召回 | `tools/session_search_tool.py` | 把历史会话变成可检索语料 | 按需 FTS5 检索 |

下面逐一拆解。

### 1.1 记忆系统：持久画像如何跨会话积累

**两层记忆。** 内置记忆是两个 Markdown 文件，定义见 `tools/memory_tool.py:6`：

- `MEMORY.md`——agent 的个人笔记与观察（环境事实、项目约定等）。
- `USER.md`——agent 对**用户**的了解（偏好、沟通风格、期望）。

`MemoryStore`（`tools/memory_tool.py:109`）负责从这两个文件加载条目，并在系统提示词里快照注入。`memory_tool`（`tools/memory_tool.py:895`）通过一个 `target` 参数区分写入哪个 store（`tools/memory_tool.py:1028`：`'memory'` 写个人笔记，`'user'` 写用户画像）。这意味着 agent 每次会话开场，系统提示词里就已经带着"它对你的全部了解"——这是跨会话连续性的最底层机制。

**可插拔的外部记忆后端。** 内置 Markdown 之外，Hermes 把"记忆"抽象成一个 provider 接口，让更强的记忆引擎可以热插拔。抽象基类是 `agent/memory_provider.py:43` 的 `MemoryProvider(ABC)`，核心生命周期（`agent/memory_provider.py:15-31` 注释列出）：

- `initialize()` 连接/建表/预热；
- `system_prompt_block()` 注入静态记忆文本；
- `prefetch(query)` 每轮**前**后台召回；
- `sync_turn(user, asst)` 每轮**后**异步写入；
- `get_tool_schemas()` / `handle_tool_call()` 暴露并分发记忆工具；
- 还有可选钩子如 `on_session_end`（会话结束抽取）、`on_pre_compress`（上下文压缩前抢救）、`on_delegation`（观察子 agent 工作）。

`agent/memory_manager.py` 的 `MemoryManager` 是唯一集成点（`agent/memory_manager.py:10-23` 给出用法）。一个关键设计约束：**同一时间只允许一个外部 provider**（`agent/memory_manager.py:6-8`），注册第二个会被拒绝并告警——这是为了避免工具 schema 膨胀和后端冲突。

`plugins/memory/` 下目前内置了多种后端：`honcho`、`hindsight`、`mem0`、`byterover`、`openviking`、`retaindb`、`supermemory`、`holographic`。以 **Honcho** 为例（`plugins/memory/honcho/__init__.py:191` 的 `HonchoMemoryProvider`），它实现了"辩证式用户建模（dialectic user modeling）"：在后台跑多轮辩证 prompt（`_build_dialectic_prompt`，`plugins/memory/honcho/__init__.py:984`）来推断"你是谁"，并在每轮前通过 `prefetch`（`:635`）把召回结果喂进上下文。这正是 README 里 "Honcho dialectic user modeling" 那句的实现。

> **为什么这让 Hermes 能自我改进？** 记忆把"易失的会话上下文"变成"持久的磁盘状态"。每次会话不是从零开始，而是从"上次结束时对你的理解"开始——理解只增不减，越用越深。

### 1.2 技能系统：完成复杂任务后自动沉淀程序性知识

如果说记忆是"agent 知道什么"，技能就是"agent 会做什么"——程序性记忆。

**技能格式（兼容 agentskills.io 标准）。** 每个技能是一个 `SKILL.md`，带 YAML frontmatter + 正文。仓库内置 72 个 `SKILL.md`，按领域分目录（`skills/creative`、`skills/software-development`、`skills/github`、`skills/research`、`skills/mlops` 等约 18 个大类）。样例见 `skills/software-development/test-driven-development/SKILL.md:1`：

```yaml
---
name: test-driven-development
description: "TDD：强制执行 RED-GREEN-REFACTOR，先写测试再写代码。"
version: 1.1.0
author: Hermes Agent (adapted from obra/superpowers)
platforms: [linux, macos, windows]
metadata:
  hermes:
    tags: [testing, tdd, development, quality]
---
```

frontmatter 的硬性规则写在 `agent/learn_prompt.py:30` 起的 `_AUTHORING_STANDARDS` 里。其中**最关键的一条**（`agent/learn_prompt.py:40-44`）：`description` 必须 ≤60 字符——因为系统提示词里的技能索引会把描述截断到 60 字，且每次会话都加载，超出部分会被静默截掉、永远无法路由。这条规则直接揭示了技能的工作原理：**所有技能的简短描述常驻系统提示词，agent 据此决定何时加载哪个技能的完整正文。**

**技能的调用与预处理。**

- `agent/skill_commands.py`：CLI 与 gateway 共享的 `/skill-name` 斜杠命令分发。当用户调用 `/skill` 时，Hermes 把这一轮展开成一个嵌入完整技能正文 + 脚手架的"模型可见消息"。
- `agent/skill_preprocessing.py`：SKILL.md 的模板预处理。支持 `${HERMES_SKILL_DIR}` / `${HERMES_SESSION_ID}` 变量替换（`agent/skill_preprocessing.py:13`）和内联 shell 片段 `` !`date` ``（`agent/skill_preprocessing.py:17`，输出截断到 4000 字防止撑爆上下文）。
- `agent/skill_bundles.py`：技能"捆绑包"。一个 YAML（存于 `~/.hermes/skill-bundles/*.yaml`）把多个技能聚合到一个斜杠命令下，`/<bundle>` 一次加载 N 个技能（`agent/skill_bundles.py:1-23`）。冲突时 bundle 优先于同名 skill（`agent/skill_bundles.py:26-31`）。

> 注意一个清洁性细节（`agent/skill_commands.py:36-46`）：技能调用被展开成包含完整技能正文的长消息，但记忆 provider 不应把整段技能正文当成"用户说的话"存起来。`extract_user_instruction_from_skill_message` 负责从展开后的消息里**只抽出用户真正的指令**，保持记忆干净。

**自动创建 / 自我改进——`/learn` 与后台复盘。**

技能有两条产生路径：

1. **手动 `/learn`**（`agent/learn_prompt.py`）：用户可以把 `/learn` 指向任何能描述的东西——一个代码目录、一个 API 文档 URL、"我刚刚带你走过的流程"、或粘贴的笔记。`build_learn_prompt` 构造**一个** prompt，指示**当前活着的 agent**用它已有的工具（`read_file`/`search_files`/`web_extract`）去搜集素材，并通过 `skill_manage` 写出一个符合标准的 `SKILL.md`（`agent/learn_prompt.py:5-22`）。没有独立的"蒸馏引擎"、没有额外模型工具足迹——这让它在 local/Docker/远程后端上行为一致。

2. **自动后台复盘**（这是"自我改进"的核心引擎，`agent/background_review.py`）：每完成 N 轮工具调用，`turn_finalizer` 会触发一次后台技能复盘（`agent/turn_finalizer.py:432-438`）。机制是 fork 一个 agent，**重放整轮对话**，问它"该不该保存/更新某个技能？"——写入直接落到技能库，主会话和 prompt cache 完全不受污染（`agent/background_review.py:1-13`）。这个 fork 的工具白名单被限制到只剩记忆和技能管理工具，其余运行时拒绝。

   后台复盘的 prompt 揭示了产品意图（`agent/background_review.py:170-204`，`_SKILL_REVIEW_PROMPT`）：

   > "Review the conversation above and update the skill library. **Be ACTIVE — most sessions produce at least one skill update.** A pass that does nothing is a missed learning opportunity, not a neutral outcome."

   它特别强调：用户的挫败信号（"stop doing X"、"this is too verbose"、"just give me the answer"、"remember this"）是**一等技能信号**——应当把偏好直接编码进相关技能，让下次会话开场就已经知道。这与记忆复盘 prompt（`agent/background_review.py:159-168`，`_MEMORY_REVIEW_PROMPT`）并列，构成"记忆 + 技能"双线沉淀。

**nudge 节奏的配置。** 两个计数器驱动 nudge：

- 技能 nudge：`agent._skill_nudge_interval`（默认 10，配置键 `skills.creation_nudge_interval`，`agent/agent_init.py:1197-1200`），每次实际用了 `skill_manage` 就重置计数（`agent/conversation_loop.py:644-648`）。
- 记忆 nudge：`agent._memory_nudge_interval`（默认 10，配置键 `memory.nudge_interval`，`agent/agent_init.py:1105-1113`）。

### 1.3 Curator：周期性策展整个技能库

后台复盘负责"往库里加东西"，**Curator 负责"维护这个库不烂掉"**（`agent/curator.py`）。

- **触发方式**：空闲触发，无 cron 守护进程。当 agent 空闲且距上次运行超过 `interval_hours`（默认 7 天，`agent/curator.py:55`）时，`maybe_run_curator()` 派生一个 fork 出来的 agent 做审查（`agent/curator.py:5-12`）。
- **职责**（`agent/curator.py:8-13`）：根据技能活动时间戳自动转换生命周期状态（stale→archive 等）；派生后台审查 agent，对**agent 创建的**技能执行 pin / archive / consolidate / patch；状态持久化在 `~/.hermes/skills/.curator_state`（`agent/curator.py:69`）。
- **严格不变量**（`agent/curator.py:14-18`，非常重要的安全设计）：
  - **只操作 agent 创建的技能**（绝不动用户手写的技能，靠 `tools/skill_usage.is_agent_created` 判定）；
  - **从不自动删除——只归档，归档可恢复**；
  - 被 pin 的技能跳过所有自动转换；
  - 使用辅助模型客户端，从不触碰主会话 prompt cache。
- 默认 `DEFAULT_CONSOLIDATE = False`（`agent/curator.py:62`）：确定性的非活动剪枝照常跑，但需要 LLM 开销的"主观合并"流程默认关闭，避免烧钱。审查 fork 内还显式禁用递归 nudge（`agent/curator.py:1841-1843`），防止 curator 自己再 spawn review。

> **为什么这让 Hermes 能自我改进？** 没有 curator，自动创建的技能会随时间膨胀成一堆窄、重复、过时的条目。curator 把库往"class-level 大技能 + references/ 细节目录"的形状收拢（与 `_SKILL_REVIEW_PROMPT` 的目标一致），保证库越大反而越好用。

### 1.4 跨会话搜索：FTS5 + 锚点窗口召回

学习闭环的最后一环是"想起以前聊过什么"。`tools/session_search_tool.py` 是单一形态工具，三种模式由参数推断（`tools/session_search_tool.py:5-26`）：

1. **发现（DISCOVERY）**：传 `query` → 跑 SQLite **FTS5** 全文索引，按会话血缘对命中去重，返回前 N 个会话，每个附带匹配位置 ±5 条的窗口，外加 bookend（会话最早/最晚各 3 条 user+assistant）。**零 LLM 开销**。
2. **滚动（SCROLL）**：传 `session_id` + `around_message_id` → 返回锚点 ±window 的窗口，可反复把窗口边缘消息当新锚点向前/后翻。
3. **浏览（BROWSE）**：不传参数 → 按时间倒序返回最近会话。

三种模式都走 FTS5 索引 + `hermes_state` 的 `get_anchored_view` / `get_messages_around` 原语操作 SQLite 会话库，**任何地方都没有 LLM 调用**——返回的全是数据库里的真实消息（`tools/session_search_tool.py:19-22`）。

> 注意 README 提到 "FTS5 session search **with LLM summarization**"，而当前实现注释（`tools/session_search_tool.py:23-26`）明确说"把所有模式合并为单一调用形态，**没有 summary LLM 路径**"。早期 PR（#20238）曾有 fast/summary 双模式，现已合并精简。**README 的 LLM 摘要措辞与现状略有出入，以代码为准。**（此点供使用者核对——*待确认 README 是否已更新*。）

子 agent 委派的会话默认从搜索/浏览里隐藏（`tools/session_search_tool.py:35`：`subagent`、`tool` 来源被排除），保证检索到的是真正的用户会话历史。

## 二、消息网关 `gateway/`

> "Lives where you do：Telegram, Discord, Slack, WhatsApp, Signal, and CLI — all from a single gateway process."

**单进程多平台。** 入口是 `gateway/run.py`（`gateway/run.py:1-14`）：`start_gateway()` 启动所有已配置的平台适配器，`GatewayRunner` 管理网关生命周期。它是一个长驻守护进程（`gateway/run.py:52` 注释强调"网关是长驻守护进程"），所以启动开销被刻意容忍以换取功能完备。

**平台适配器注册表。** 网关不靠硬编码的 if/elif 链发现平台，而是用注册表 `gateway/platform_registry.py`。`PlatformEntry`（`gateway/platform_registry.py:38`）是单个平台的元数据 + 工厂：`name`、`label`、`adapter_factory`（接收 `PlatformConfig` 返回 adapter 实例）、`check_fn`（依赖是否可用）、`validate_config` 等。插件侧通过 `platform_registry.register(PlatformEntry(...))` 注册（`gateway/platform_registry.py:11-23`），网关侧用 `create_adapter("irc", config)` 实例化。插件平台优先查找，找不到才回退到内置 `_create_adapter()` 的遗留路径（`gateway/platform_registry.py:5-9`）。

**平台清单。** 内置平台在 `gateway/platforms/`（signal、whatsapp_cloud、qqbot、weixin、yuanbao、bluebubbles 等），更多平台作为插件在 `plugins/platforms/`：telegram、discord、slack、whatsapp、email、feishu、teams、line、matrix、mattermost、irc、sms、dingtalk、wecom、google_chat、homeassistant、ntfy、simplex、raft、photon……合计约 20+ 平台。每个平台一个 `adapter.py`。

**跨平台会话连续性。** 会话管理在 `gateway/session.py`（`gateway/session.py:1-9`），负责：会话上下文跟踪（消息来自哪个平台/频道）、对话持久化到磁盘、重置策略评估（何时开新会话）、动态系统提示注入（让 agent 知道自己当前在哪个上下文里）。配合 PII 脱敏（`gateway/session.py:34-40` 把发送者 ID 哈希成 `user_<12hex>`）。因为会话状态是平台无关地持久化的，所以你可以在 Telegram 起个话题、切到 Discord 继续——这就是 README 说的 "cross-platform conversation continuity"。

**语音转写。** README 列出 "Voice memo transcription"——平台收到语音 memo 时转写成文本喂给 agent（相关依赖在安装时通过 voice extra 引入，Termux 因 Android 不兼容而被排除，见 README 第 57 行）。*具体转写后端实现位置待确认。*

## 三、定时任务 `cron/`

> "Scheduled automations：Built-in cron scheduler with delivery to any platform … all in natural language, running unattended."

**调度执行。** `cron/scheduler.py` 提供 `tick()`：检查到期任务并运行，网关每 60 秒从后台线程调用一次（`cron/scheduler.py:1-9`）。用文件锁 `~/.hermes/cron/.tick.lock` 保证多进程重叠时只有一个 tick 在跑（跨平台：Unix 用 `fcntl`，Windows 回退 `msvcrt`，`cron/scheduler.py:24-32`）。

**任务存储。** `cron/jobs.py`：任务存于 `~/.hermes/cron/jobs.json`，每次运行的输出落到 `~/.hermes/cron/output/{job_id}/{timestamp}.md`（`cron/jobs.py:1-6`）。用 `croniter` 解析 cron 表达式（`cron/jobs.py:42-46`）。jobs.json 的临界区用跨进程文件锁保护（同样 fcntl/msvcrt 回退，`cron/jobs.py:24-31`）。

**面向 agent 的工具。** `tools/cronjob_tools.py` 暴露一个**压缩的、面向动作的**单工具（避免 schema/上下文膨胀，`tools/cronjob_tools.py:1-6`），内部封装 `cron.jobs` 的 `create_job` / `list_jobs` / `update_job` / `pause_job` / `resume_job` / `remove_job` / `parse_schedule` 等（`tools/cronjob_tools.py:22-35`）。agent 用自然语言描述"每天早上 8 点给我发昨天的 GitHub 摘要到 Telegram"，工具把它落成一条 cron job，调度器到点 fork 一个 agent 执行并把结果**投递到指定平台**。

**自然语言与蓝图。** `cron/blueprint_catalog.py`、`cron/suggestions.py`、`cron/suggestion_catalog.py` 提供任务蓝图与建议（常见自动化模板：日报、夜间备份、周审计）。`cron/scheduler_provider.py` 让 cron provider 可插拔（`plugins/cron_providers/`）。安全上，`tools/cronjob_tools.py:48-` 起有针对"用户提供的 cron 提示词"和"agent 自己写的提示词"两个威胁面的扫描器。

> **为什么这与自我改进相关？** cron 让 agent 能"无人值守地持续工作"——它不只是被动应答，而是按节奏主动产出。配合记忆/技能，定时任务的产物也能反过来沉淀进库。

## 四、插件与 providers：一切皆可插拔

Hermes 的特色之所以能"无锁定地接入任意后端"，靠的是统一的插件体系。

**`plugins/`——按能力域分目录的插件树。** 顶层包括：

- `model-providers/`：模型提供商（deepseek、gemini、nous、openrouter、novita、nvidia、xai、zai、kimi-coding、minimax、xiaomi、ollama-cloud、openai-codex 等约 20 家）。
- `memory/`：记忆后端（见 §1.1）。
- `platforms/`：聊天平台适配器（见 §2）。
- `web/`：网页搜索 provider（brave_free、ddgs、exa、firecrawl）。
- `image_gen/`、`video_gen/`、`observability/`（langfuse）、`browser`、`context_engine`、`cron_providers`、`kanban`、`spotify`、`google_meet`、`teams_pipeline` 等。

**`providers/`——推理 provider 的注册表与 ABC。** 注意区分（`providers/README.md:1-25`）：`providers/` 只放**注册表和 `ProviderProfile` 数据类**（`providers/base.py`）；**具体的 profile 本体作为插件住在 `plugins/model-providers/<name>/`**。注册表在首次访问时惰性发现这些插件（`get_provider_profile()` / `list_providers()`）。每个 provider 只声明一次 `ProviderProfile`，其余所有层（鉴权解析、传输 kwargs、模型列举、运行时路由）都从 profile 读，不再各自维护平行数据。这就是 README 说的 `hermes model` 一键切换、"no code changes, no lock-in" 的实现基础。

> 一句话区分：**`plugins/` 是"插件实现住的地方"，`providers/` 是"模型 provider 的注册中枢"。** 模型 provider 横跨两者：注册逻辑在 `providers/`，profile 数据在 `plugins/model-providers/`。

## 五、其他特色（简要）

- **MCP 集成（`mcp_serve.py`）**：`hermes mcp serve` 启动一个 stdio MCP 服务器，把 Hermes 的消息对话**作为 MCP 工具暴露**给任意 MCP 客户端（Claude Code、Cursor、Codex 等）。提供 conversations_list、messages_read、messages_send、events_poll、permissions_respond 等工具（`mcp_serve.py:3-12`），对齐 OpenClaw 的 9 工具频道桥接接口并加了 `channels_list` 扩展。即 Hermes 既能当 MCP host 接别人的 server，也能当 MCP server 被别人接。
- **子 agent 委派**：spawn 隔离的子 agent 跑并行工作流；记忆 provider 还能通过 `on_delegation` 钩子（`agent/memory_provider.py:30`）在父侧观察子 agent 的产出。委派会话默认从会话搜索里隐藏。
- **个性化 `personality` / `SOUL.md`**：persona 文件（仓库内样例见 `docker/SOUL.md`；OpenClaw 迁移时 `SOUL.md` 是首批导入项，README:204）。`/personality [name]` 在 CLI 与 gateway 都可切换人格。

## 六、把闭环连起来：一次完整的"自我改进"

用一个场景串起本章：

1. 你在 **Telegram**（§2 网关）发语音说"以后给我写 commit message 别用感叹号"。语音被转写成文本。
2. agent 照做。会话状态持久化（`gateway/session.py`），跨平台可续。
3. 这一轮结束，计数器到阈值 → **后台复盘 fork**（§1.2，`background_review.py`）重放对话，识别出"用户纠正了风格"这个一等技能信号，把偏好 **patch 进相关技能**，同时把"你不喜欢感叹号"写进 **`USER.md`**（§1.1）。主会话毫无感知，prompt cache 不受污染。
4. 一周后空闲时，**Curator**（§1.3）巡检技能库，把这条偏好所在的技能往 class-level 形状收拢，归档掉过时的窄技能。
5. 下次你在 **Discord** 开新会话——系统提示词开场就带着 `USER.md` 的画像和那条技能的描述索引。你**不用再说一遍**，agent 已经知道。
6. 三个月后你忘了当时怎么配的某个流程，用 **会话搜索**（§1.4，FTS5）一搜就翻回当时的上下文。
7. 你还可以让它把"每周技能审计报告"设成 **cron**（§3），无人值守地发到你手机。

每一环都把"这次学到的"变成"下次的起点"——这就是 Hermes 自我改进的闭环。
