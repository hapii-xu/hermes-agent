一、三个入口脚本（[project.scripts]）

入口在 pyproject.toml:296-299 定义：

[project.scripts]
hermes       = "hermes_cli.main:main"
hermes-agent = "run_agent:main"
hermes-acp   = "acp_adapter.entry:main"
命令入口函数职责
hermes hermes_cli/main.py:12022 的 main() 面向人类用户的主 CLI。日常入口：交互式聊天、gateway / setup / cron / model / doctor / mcp 等所有子命令的总调度。内部用 argparse 构建一棵庞大的子命令树。
hermes-agent run_agent.py:5357 的 main() agent 核心的直接运行器 / 库入口。把 AIAgent（run_agent.py:334）作为独立可嵌入的"带工具调用的对话循环"暴露出来。可用 fire 当 CLI 跑，也被 cli.py、batch_runner.py、RL 环境作为库导入。它是"裸 agent"，不带 TUI/REPL。
hermes-acp acp_adapter/entry.py 的 main() ACP（Agent Client Protocol）服务器适配器，用于编辑器集成（如 acp-bridge）。stdout 留给 ACP 的 JSON-RPC 传输，等价于 hermes acp 子命令。
三者的共同点：每个入口文件的第一件事都是 import hermes_bootstrap，且都用 try/except ModuleNotFoundError 包裹——原因见第五节。

二、启动链路：敲下 hermes 之后发生了什么

以最常见的「交互式聊天」为例（直接 hermes 或 hermes chat）：

三个层次的分工：
  • hermes_cli/main.py 只做「路由 + 环境自愈」，不含 agent 逻辑。
  • cli.py 提供 TUI/REPL 外壳（prompt_toolkit），并持有一个 AIAgent 实例。
  • run_agent.py 的 AIAgent 才是 agent 核心——可脱离 CLI 单独运行，也被 gateway、batch、RL 复用。

三、整体架构分层与「窄腰」设计

┌──────────────────────────────────────────────────────────────────┐ │ 边缘 (edges) —— 能力在这里疯狂生长，鼓励扩张 │ │ │ │ hermes_cli/ CLI 子命令（setup/model/cron/mcp/doctor/...） │ │ gateway/ 消息网关：Telegram/Discord/Slack/Matrix... ~20 平台 │ │ cron/ 内置定时调度器（croniter） │ │ plugins/ 运行时发现的插件（平台适配器、搜索 provider 等） │ │ skills/ 技能（指令式 Markdown + 脚本），可自我创建/改进 │ │ tools/ ~100+ 工具实现，各自向 registry 自注册 │ ├──────────────────────────────────────────────────────────────────┤ │ 窄腰 (narrow waist) —— 极度克制，每加一个核心工具都很贵 │ │ │ │ agent/ agent 核心（对话循环、上下文、记忆、压缩、prompt） │ │ run_agent.py AIAgent：带工具调用的对话循环 │ │ model_tools.py 工具注册表之上的薄编排层（决定哪些工具上桌） │ │ toolsets.py 工具集（命名分组，跨平台共享） │ └──────────────────────────────────────────────────────────────────┘

「窄腰（narrow waist）」核心要点

  • 按对话的 prompt 缓存是神圣的（AGENTS.md:19-23）：任何中途改写历史、换工具集、重建系统提示的行为都会击穿缓存，让用户成本翻倍——所以坚决不做（唯一例外是上下文压缩）。
  • 核心是窄腰，能力住在边缘（AGENTS.md:24-27）：每一个核心 model tool 都会在每次 API 调用时被发送，所以新增核心工具的门槛极高。
  • 「在边缘扩张，在窄腰克制」（AGENTS.md:43-50）：产品面（平台/渠道/provider/模型/桌面功能）鼓励大胆增长，唯独核心 agent + model tool schema 要省到底，因为它在每次 API 调用上都要付费。

四、进程模型

Hermes 是多进程架构。hermes_logging.py:37-44 的注释直接点名了同时写 agent.log 的多个独立进程：「TUI、gateway、hy_memory server、MCP servers，以及按需的 CLI 命令」。

进程由谁启动职责
CLI / TUI 进程 hermes / hermes chat 前台交互式会话。持有一个 AIAgent，跑 prompt_toolkit 循环。
gateway 进程 hermes gateway start → gateway/run.py:start_gateway 常驻服务，单进程驱动所有消息平台适配器 + cron 投递。每个会话在内部用 agent core。
MCP server 进程 hermes mcp serve（mcp_serve.py） stdio MCP 服务器，把「消息对话」作为 MCP 工具暴露给 Claude Code / Cursor 等外部 MCP 客户端。
memory server 进程（hy_memory） 记忆后端按需拉起 独立的记忆服务进程（与 agent/memory_manager.py 配合）。
子进程（短命） agent 工具调用 execute_code 沙箱、delegate 委派的子 agent、linter 等，由 agent 在工具执行时 subprocess 派生。

跨进程协作的关键细节

日志

所有进程都写 ~/.hermes/logs/。Windows 上多进程同时持有 agent.log 句柄，标准库的 RotatingFileHandler 会触发 WinError 32，所以 Windows 专门换成 concurrent-log-handler（跨进程文件锁，hermes_logging.py:37-60）。

UTF-8 引导

hermes_bootstrap 在每个入口顶端设置 PYTHONUTF8 / PYTHONIOENCODING，子进程继承这些环境变量，从而让派生出的每个 Python 子进程也走 UTF-8（hermes_bootstrap.py:9-26, 71-75）。

五、关键顶层模块速查表

行数即「体量」，上万行者为典型 god file（AGENTS.md:64-70 明确把 cli.py / run_agent.py / gateway/run.py 列为可被重构拆分的 god file，且这类大型机械重构是受欢迎的工作）。

模块行数一句话职责god file?
cli.py~15,487交互式终端外壳：prompt_toolkit TUI/REPL、HermesCLI 类、main() 入口，持有 AIAgent。是（最大）
hermes_cli/main.py~13,230hermes 命令的 argparse 路由 + 子命令注册 + 启动期环境自愈。是
run_agent.py~5,573AIAgent 类与对话循环；agent 核心，可作库/CLI 独立运行。是
hermes_state.py~5,103基于 SQLite 的会话状态存储（WAL 并发 + FTS5 全文检索），存会话元数据/消息历史/模型配置。是
model_tools.py~1,256工具注册表之上的薄编排层：触发工具发现、决定哪些工具上桌、分发 handle_function_call。偏大
mcp_serve.py~903hermes mcp serve 的 stdio MCP 服务器，把对话作为 MCP 工具暴露。中等
toolsets.py~933工具集定义 + 跨平台共享的核心工具列表 _HERMES_CORE_TOOLS。中等
hermes_constants.py~733无依赖、导入安全的共享常量（get_hermes_home() / get_config_path() 等）；可从任意处导入无循环风险。否
hermes_bootstrap.py~187Windows UTF-8 stdio 引导 + harden_import_path()；必须第一个被导入，POSIX 空操作。否
为什么 hermes_bootstrap 用 try/except ModuleNotFoundError 包裹？
hermes update 若在 git reset --hard 和 uv pip install -e . 之间崩溃，新代码引用了它但可编辑安装的 .pth 仍指向旧模块集——加保护可避免「导入即崩溃、连 hermes update 都跑不起来」的死锁（hermes_cli/main.py:46-62）。

六、配置体系：config.yaml vs .env

出处：AGENTS.md:103-107。两者职责严格分离，这是项目的硬规则：

config.yaml.env
存什么所有行为设置：默认模型、provider、超时、阈值、功能开关、显示偏好……只存机密：API key、token、密码。
位置~/.hermes/config.yaml（profile 感知）~/.hermes/.env
谁改hermes setup / hermes model 等命令，或手改 YAML用户填入凭证
优先级—.env 里的环境变量优先于 config（cli-config.yaml.example:3）
硬性约束：
  • 禁止为非机密配置新增 HERMES_* 环境变量。一切行为开关都进 config.yaml；即使内部机制需要一个环境变量做桥接，面向用户的文档也必须指向 config.yaml。
  • 任何告诉用户「把 X 设进 .env」的 PR 会被拒——除非 X 是凭证。

一眼看懂的对应关系

hermes (人用 CLI) → hermes_cli/main.py:main → cmd_chat → cli.py:main → HermesCLI → AIAgent hermes-agent (裸 agent) → run_agent.py:main → AIAgent.run_conversation hermes-acp (编辑器集成) → acp_adapter/entry.py:main → ACP server (stdout=JSON-RPC) hermes gateway start → gateway/run.py:start_gateway （独立常驻进程） hermes mcp serve → mcp_serve.py （独立 MCP server 进程）
