一、环境搭建（uv）

1.1 为什么是 uv

项目用 uv（Astral 出品的 Rust 写的 Python 包管理器）管理依赖，而不是 pip/poetry。Windows 一键安装脚本（iex (irm https://hermes-agent.nousresearch.com/install.ps1)）会自动装好 uv、Python 3.11、Node.js、ripgrep、ffmpeg，以及一份便携版 Git Bash（MinGit），解压到 %LOCALAPPDATA%\hermes\git，不需要管理员权限。

Windows 杀软误报：部分杀软（Bitdefender / Windows Defender）会把 %LOCALAPPDATA%\hermes\bin\uv.exe 当成病毒隔离，这是误报——它就是 Astral 的 uv。需要把 bin 文件夹加白名单（别加文件哈希，因为升级后哈希会变）。

1.2 两条安装路径

路径 A（推荐 / 贡献者标准路径）

先跑标准安装器，再在它克隆出的完整 git 仓库里加装开发依赖。这样你的开发环境布局和 CLI、hermes update、懒加载依赖、gateway 假设的布局完全一致（README.md:220-230）。完整仓库位于 $HERMES_HOME/hermes-agent。

路径 B（手动 clone，本机当前就是这种）

适合一次性 clone、容器或 CI。PowerShell 命令：
uv venv .venv --python 3.11
.\.venv\Scripts\Activate.ps1
uv pip install -e ".[all,dev]"

Python 版本上限：requires-python = ">=3.11,<3.14"（pyproject.toml:20）。上限是有意为之，不是摆设：封到 <3.14 让 uv 直接报清晰错误而不是闷头编译（pydantic-core 等 Rust 后端在 3.14 上还没有 cp314 wheel）。

1.4 依赖锁定策略（供应链安全）

dependencies 里每个直接依赖都是精确钉死 ==X.Y.Z，没有范围。原因：

  • 范围允许 PyPI 随时推一个新的传递依赖版本，绕过我方代码评审。精确 pin 意味着新版本只能通过"我方主动改 pin + 重新生成 uv.lock"才会到达用户。
  • 这条策略是 2026-05-12 收紧的，起因是 Mini Shai-Hulud 蠕虫攻击了 PyPI 上的 mistralai 2.4.6。
  • 改依赖的正确姿势：改 pyproject.toml 里的 pin 并 uv lock 重新生成 uv.lock。不要随意把范围加回来。

1.5 Windows 原生支持的关键依赖

依赖作用
pywinpty>=2.0.0,<3Windows 下的伪终端（PTY），对应 POSIX 的 ptyprocess。终端工具靠它。
tzdataWindows 系统不自带 IANA 时区库，Python 的 zoneinfo 对任何非 UTC 时区都会抛 ZoneInfoNotFoundError，靠这个数据包补上。
concurrent-log-handlerWindows 日志轮转专用（见日志系统一节）。
psutil跨平台进程/PID 管理，替代在 Windows 上会"静默杀错进程"的 os.kill(pid, 0)。

三、如何 Debug

3.1 第一站：hermes doctor

任何"装好了但跑不起来"的问题，先跑 hermes doctor（实现见 hermes_cli/doctor.py）。它会检查 LLM provider key、系统依赖、浏览器可运行性等，并按平台给出对应的安装命令（Windows 上给 uv pip install / winget）。

3.2 用 debugpy 挂调试器

debugpy==1.8.20 在 dev extra 里（pyproject.toml:157）。仓库里没有内建的"自动启动 debugpy 监听端口"的开关，需要你手动注入。两种方式：

方式一：在代码里临时插入监听（适合调长生命周期进程，如 gateway）

import debugpy
debugpy.listen(("127.0.0.1", 5678))
print("debugpy listening on 5678, waiting for client...", flush=True)
debugpy.wait_for_client()   # 阻塞直到 VS Code attach

然后在 VS Code 用 "Python: Attach" 连 127.0.0.1:5678。

方式二：从命令行用 debugpy 启动 CLI

.\.venv\Scripts\python.exe -m debugpy --listen 5678 --wait-for-client -m hermes_cli.main chat -q "Hello"

3.3 分模块的 DEBUG 环境变量开关

环境变量作用代码位置
HERMES_LOG_LEVEL调整日志级别（如 DEBUG），让更多细节写进日志文件hermes_cli/auth.py:2473

$env:WEB_TOOLS_DEBUG = "true"; hermes chat -q "搜一下今天的新闻"

这些开关背后是统一的基础设施 tools/debug_helpers.py 的 DebugSession 类（debug_helpers.py:36-58）：关闭时所有方法都是几乎零开销的空操作；开启时把每次工具调用记成 JSON 写到 ~/.hermes/logs/。

3.4 流式诊断（stream_diag）

当流式 chat-completions 请求在中途断掉，agent/stream_diag.py 会收集"为什么断"的诊断信息：哪个 Cloudflare 边缘节点、OpenRouter 下游用了哪个 provider、断前收到多少字节/chunk、HTTP 状态、底层 httpx 异常类。排查"模型回到一半断流"时，去 agent.log 搜 cf-ray、x-openrouter-provider 等字段。

四、日志系统

集中式配置在 hermes_logging.py，单一入口 setup_logging()。生成的文件都在 ~/.hermes/logs/：

文件内容
agent.logINFO+，所有 agent/工具/会话活动（主日志，兜底）
errors.logWARNING+，只有错误和警告（快速排查首选）
gateway.loggateway 专属事件（mode="gateway" 时）
gui.logdashboard / websocket / TUI-gateway 事件

每条日志带 [session_id] 标签（set_session_context() 注入），可按会话过滤关联。所有 handler 用 RedactingFormatter，密钥永远不会落盘。

# PowerShell 实时看日志
Get-Content "$HOME\.hermes\logs\agent.log" -Wait -Tail 50    # 类似 tail -f
Get-Content "$HOME\.hermes\logs\errors.log" -Tail 30         # 只看错误
Windows 日志轮转的坑（hermes_logging.py:37-58，必读）：
stdlib 的 RotatingFileHandler.doRollover() 用 os.rename()，当另一个进程以追加模式持有 agent.log 句柄时会抛 PermissionError [WinError 32]——而 Hermes 里这几乎是常态（TUI、gateway、hy_memory、MCP server 都从独立进程写日志）。

解决方案：仅在 Windows 把 RotatingFileHandler 别名为 concurrent-log-handler 的 ConcurrentRotatingFileHandler（用 portalocker/pywin32 做跨进程文件锁），POSIX 上保持 stdlib 不变。参见 issue #44873。

hermes debug share

要把环境信息 + 日志发给别人求助，用 hermes debug share（hermes_cli/debug.py）。它默认在上传前对日志脱敏（redact_sensitive_text(force=True)），把 logs/*.log 里的凭据擦掉再传到 paste 服务，返回一个 6 小时后自动删除的 URL。

5.2 跑测试：scripts/run_tests.sh（务必用它）

铁律（AGENTS.md:1252）：永远用 scripts/run_tests.sh，不要直接调 pytest。
因为脚本强制了与 CI 一致的"洁净环境"，否则一台 16+ 核、设了 API key 的开发机会和 CI 产生分歧，多次造成"本地过 CI 挂"或反过来的事故。
这是 bash 脚本，Windows 上要用项目自带的 Git Bash 跑（%LOCALAPPDATA%\hermes\git）。

脚本做的事：

  • 通过 scripts/run_tests_parallel.py 做每文件隔离——每个测试文件在自己新生成的 python -m pytest <file> 子进程里跑，杜绝模块级状态泄漏。
  • 强制 TZ=UTC、LANG=C.UTF-8、PYTHONHASHSEED=0（确定性）。
  • 用 env -i 清空环境再 opt-in，任何凭据变量都不会泄露进测试（run_tests.sh:62-80）。
# Git Bash 里运行
scripts/run_tests.sh                                  # 全量，CI 对齐
scripts/run_tests.sh tests/gateway/                   # 单个目录
scripts/run_tests.sh tests/agent/test_foo.py          # 单个文件
scripts/run_tests.sh tests/agent/test_foo.py::test_x  # 单个用例
scripts/run_tests.sh -j 4                             # 限制并行度
scripts/run_tests.sh -- -v --tb=long                  # `--` 之后透传给 pytest
scripts/run_tests.sh --no-isolate tests/foo/          # 关闭子进程隔离（调试时更快）

5.3 pytest 配置（pyproject.toml）

  • testpaths = ["tests"]
  • markers：integration（需要外部服务）、real_concurrent_gate
  • addopts = "-m 'not integration'" —— 默认就跳过 integration 测试。要专门跑：scripts/run_tests.sh -- -m integration。
  • 异步测试用 pytest-asyncio==1.3.0，可以直接写 async def test_...。

5.4 测试理念（AGENTS.md，写测试前必读）

行为契约 > 快照（Behavior contracts over snapshots）：
测试要断言"两份数据之间的关系/不变量"，而不是冻结某个当前值。反例叫 change-detector test——每次模型目录更新、配置版本号 +1、枚举数量变化就挂，纯属浪费工程时间。

不要写：assert "gemini-2.5-pro" in _PROVIDER_MODELS["gemini"]、assert len(...) == 8
要写：assert "gemini" in _PROVIDER_MODELS、"目录里每个模型都有 context-length 条目"这类不变量。

判断法则：像当前数据快照的就删，像两份数据必须满足的契约的就留。
E2E 真实路径 > 全绿的 mock 单测（AGENTS.md:84-87）：
凡是碰到解析链、配置传播、安全边界、远程后端、文件/网络 I/O 的，要用真实 import 跑真实路径（针对临时 HERMES_HOME），别用 mock —— mock 会藏住集成 bug。

临时 HOME 的坑：mock Path.home() 的测试也要设 HERMES_HOME，否则代码走的是 HERMES_HOME 而非 home()。

5.5 跨平台测试（Windows 相关）

# POSIX-only 的系统调用需要 skip 标记
@pytest.mark.skipif(sys.platform == "win32", reason="symlink/POSIX-only")
def test_symlink_behavior():
    ...

常见需要跳过的：符号链接、0o600 文件模式、signal.SIGALRM、os.setsid/os.fork。Windows 专属回归测试反过来用 skipif(sys.platform != "win32", ...)。

六、代码质量工具

6.1 ruff（只开一条规则）

[tool.ruff]（pyproject.toml:364-383）的配置非常特殊：几乎所有 lint 都关了，只开 PLW1514（unspecified-encoding）。

原因：裸 open() / read_text() / write_text() 在文本模式下默认用系统 locale 编码，Windows 上（US locale）是 cp1252，会静默损坏任何非 ASCII 文件内容——他们在一次调试里连踩三个 Windows 沙箱回归才加了这条强制规则。

写文件时一定要显式指定编码：
path.read_text(encoding="utf-8")
open(path, "w", encoding="utf-8") 
.\.venv\Scripts\ruff.exe check .

6.2 ty（类型检查）

ty==0.0.21（Astral 的类型检查器）在 dev extra 里。配置：python-version = "3.13"、unknown-argument = "warn"。

.\.venv\Scripts\ty.exe check .

debug 一个工具调用的示例思路

假设你怀疑 web_search 工具行为异常，排查路径：

  1. 1
    先看现象Get-Content $HOME\.hermes\logs\errors.log -Tail 30 看有没有报错；再翻 agent.log 找对应 [session_id]。
  2. 2
    开工具级 debug 开关$env:WEB_TOOLS_DEBUG = "true"，再复现一次。DebugSession 会把每次调用（query、结果数等）写成 JSON 到 ~/.hermes/logs/。
  3. 3
    挂调试器看实参/控制流在 tools/web_tools.py 里要断的位置插入 debugpy.listen 三行，或用 python -m debugpy --listen 5678 --wait-for-client -m hermes_cli.main chat -q "..."，VS Code attach 到 5678。
  4. 4
    若是流式中断去 agent/stream_diag.py 关注的响应头（x-openrouter-provider 等）在 agent.log 里找断流原因。
  5. 5
    写一个行为契约测试固化修复放到 tests/tools/，断言"输入 → 输出关系"的不变量，用真实 import 跑真实路径。涉及外部 API 的标 @pytest.mark.integration。
  6. 6
    提交前自检ruff check .、ty check .、python scripts\check-windows-footguns.py --diff main，再用 Git Bash 跑 scripts/run_tests.sh tests/tools/。
